# Consent Audit Viewer — beta21

Актуальное изменение beta29: [инструкция](modx2-beta29-update.md), [приёмка](modx2-beta29-acceptance.md). Журнал использует одну колонку layout без preview и четыре колонки таблицы: дата/время, IP, действие, детали. IP входит в summary уже валидированной записи; поиск/пагинация/CSV/ACL прежние. Ниже — исходная документация beta21.

Viewer реализован во вкладке «Журнал» Cookie Consent Manager на MODX 2.8.8 / PHP 8.1+. Основа — immutable beta15 с серверно-независимой настройкой журнала. Установка — штатный Package Manager, без Setup Options, SQL-таблиц событий, lifecycle ledger и скрытых копий персональных данных.

## Права

Новое разрешение `cookie_consent_view_logs` определяется в MODX access policy templates с default=false. Пакет не добавляет его в существующие policies и не предоставляет его всем пользователям Manager. Administrator/sudo сохраняет штатный обход ACL MODX.

Назначьте разрешение выбранной группе через стандартные access policies MODX, обновите права/сессию пользователя. Для полной страницы компонента нужен также `cookie_consent_manage`. Роль только с правом чтения может открыть `manager/?a=logs&namespace=cookie_consent`: там отсутствуют Save, services/texts и настройки хранения. Существующее меню с manage permission сохраняется — MODX проверяет его до вызова controller, поэтому read-only route отдельный и не требует перезаписывать пользовательское меню.

`logs_list`, `logs_detail`, `logs_export` независимо проверяют authenticated mgr + view_logs. Save/setup/reconsent по-прежнему требуют manage. Это права component endpoints; отдельные права native File Manager, media sources, DB и ОС не отзываются этим компонентом. Если журнал находится в webroot и пользователь имеет доступ к нему через File Manager, ограничьте media-source/файловые права отдельно.

## Интерфейс

Журнал начинается с фильтров: текущий UTC календарный год, все месяцы, все действия и пустой поиск. Годы перечисляются по именам существующих месячных файлов; «Все годы» применяется только явным выбором. «Найти» фиксирует выбранные значения. Простое изменение полей не отправляет запросы; переходы между страницами и CSV используют последние применённые фильтры.

Под фильтрами одна строка с точным числом результатов слева и CSV справа. В таблице ровно три столбца: UTC дата/время, локализованное действие, «Просмотр». Загружается до 50 строк. Next/Previous используют курсор, а не загрузку всей истории в браузер. Неизвестный event показывается как «Другое событие»; исходный тип остаётся в details и фильтре. Поддерживаемые типы включают шесть стандартных действий и дополнительные корректные типы из прочитанных файлов.

Details безопасно показывают server/client time, schema, event/stage, IP/User-Agent, consent/event ID, разрешённые/отклонённые категории, старые/текущие provider permissions, страницу, policy version и provider события. Все значения выводятся через textContent. Кнопка истории устанавливает Consent ID в поиск и явно выбирает все годы. Настройки хранения и прежнее включение аудита находятся в сворачиваемом разделе после таблицы.

## Формат и запись

Новый месячный файл:

```text
# Cookie Consent Manager audit log
{"schema":2,"server_time":"2026-10-12T19:00:00Z",...}
```

Это **не строгий JSONL**, а header-aware формат JSON-записей по строкам. Имя остаётся `YYYY-MM-cookie-consent.log`. При создании файла logger использует exclusive create, существующий глобальный limiter lock и monthly flock. Заголовок записывается один раз под блокировкой, перед событием. Существующие файлы, включая пустые, не получают заголовка задним числом; обычное добавление событий сохраняет старый префикс. При частичной записи действует прежний truncate к позиции до новой записи; старые записи не удаляются.

Общий parser принимает старый формат и точный известный header только в начале первой строки. Неизвестные комментарии, повторный header, неправильный JSON/schema/record/time и слишком длинные строки получают диагностику. Viewer продолжает показывать корректные записи; POST-check/утилиты не подтверждают чтение повреждённой строки молча. Заголовок/MIME и открытие в native File Manager проверены отдельно.

## Чтение, CSV и большие файлы

Reader открывает только ожидаемые месячные имена из server-side log_dir, проверяет canonical directory/родители, symlink, regular file/single link и inode identity открытого файла. После создания reader повторная подмена каталога на symlink отклоняется. Путь/имя/offset от клиента не разрешают произвольное чтение; detail locator проверяется и сверяется с digest строки. Reader не требует PHP write permission и не зависит от audit key или типа сервера.

Каждый поиск/переход сканирует выбранные файлы: точный count корректных совпадений и bounded heap из 50 summaries. Сортировка глобально по server_time, затем имени файла/offset для равных времён, независимо от физического порядка строк. Память не растёт с количеством событий, но время — O(число строк). Для миллионов записей нужен запас времени запроса; UI показывает чтение, processors допускают до 120 секунд CPU. Slow filesystem/proxy timeouts на конкретном staging проверяются владельцем.

Перед чтением фиксируются EOF sizes под коротким shared lock. Поздние append не попадают в этот запрос; writer не блокируется на весь scan. Это не глобальная транзакция между разными файлами или страницами. При удалении/сокращении/подмене файла возвращается безопасная ошибка; недоступные файлы не дают ложного «точного» total. Повреждённые строки не считаются событиями: их число и до 100 безопасных диагностик показаны отдельно. Неизвестные неподдерживаемые поля скрываются с предупреждением; конфигурационные secrets не экспортируются. Каталог типов событий ограничен 256 значениями для защиты памяти, сами корректные события сохраняются в результатах.

CSV — UTF-8 с BOM, separator `;`, 17 локализованных колонок: server_time, event, IP, UA, IDs, категории, providers, page, policy, stage, client_time, provider, schema, source и diagnostics count. Кавычки/переносы экранируются fputcsv, опасные formula prefixes получают apostrophe. Выгружаются все корректные совпадения, а не 50 строк. CSV имеет порядок source file/line; table имеет сортировку по времени. Export делает предварительную проверку/count и потоковое чтение того же EOF snapshot, без temporary PII files. Браузер скачивает ответ native POST form, без fetch/blob истории в JavaScript.

Диагностики отражаются в Viewer, CSV diagnostic column и response headers. Если чтение отказало во время уже начатой передачи, CSV заканчивается явной строкой «ЭКСПОРТ НЕ ЗАВЕРШЁН»; повторите выгрузку. Атомарная доставка CSV при сетевых/файловых отказах не обещается.

## Установка / обновление

1. Backup DB/registry key, core/assets, настройки, элементы/props, legacy config и все журналы.
2. Проверить SHA256 beta21 и установить через Package Manager. Settings/HTML/переводы/services/props, ID/type/metadata элементов, audit key и журналы сохраняются; canonical code четырёх элементов и runtime обновляются. Новые stock copies не создаются. Нет автоматических изменений шаблонов или `.htaccess`.
3. Назначить view_logs нужным группам; существующие manage permissions сохраняются. Проверить RU/EN, фильтры, details и CSV на своём staging.
4. Для настройки журнала раскрыть «Настройки хранения», выбрать существующий PHP-writable каталог и нажать «Проверить и включить журнал». Старые записи/файлы не мигрируются и не удаляются.

Журналы могут содержать IP-адреса и технические сведения о посетителях. Ограничение HTTP-доступа к каталогу обеспечивает администратор сайта
