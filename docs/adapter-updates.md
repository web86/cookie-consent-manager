# Обновление адаптеров и сборка на установленном сайте

Кандидат MODX 2: 1.0.7-beta1 от main 1.0.6. MODX 3 переносится в своей ветке после приёмки MODX 2. Это изменение модели установки; оно не исправляет существующие release gates внешних сервисов или MODX 3 Fenom.

## Native install/upgrade

1. Первый штатный script vehicle preflight проверяет PHP/extensions, canonical paths, writable destinations, штатный backup, каталог bundle и возможность записи. Он читает **предыдущий** frontend-manifest.json до file vehicles, сохраняет manifest/version только в request-local MODX options и захватывает существующий cookie-consent.build.lock.
2. Native object/file vehicles сохраняют прежние правила canonical elements и строгую allowlist. Вместо public services/ каждый пакетный оригинал устанавливается в core/components/cookieconsent/adapters/services/. Файлы посетительского каталога services/ не являются targets ни одного vehicle. CSS и остальные исходники поставляются по прежней схеме. Production cookie-consent.min.js отсутствует в ZIP.
3. Финальный штатный verification vehicle проверяет SHA256 всех пакетных файлов, включая приватные оригиналы, canonical DB sources, permissions и install hook. CookieConsentAdapterInstall синхронизирует только явно перечисленные services inputs, затем тот же CookieConsentBundleManager строит PHP/Peast bundle. Вся синхронизация/сборка использует один существующий lock; Manager rebuild во время установки получает bundle_busy.
4. Atomic rename, source fingerprint, initialization guard, ES2020 parsing и сохранение cookie_consent.bundle_version после публикации остаются прежними. Неизменённый fingerprint допускает skip. Ошибка компиляции не заменяет предыдущий bundle и timestamp.

## Контрольные суммы

frontend-manifest.json остаётся каноническим упорядоченным списком inputs. Добавлено package_version; SHA256 относятся к **оригиналам пакета**, а не к пользовательским bytes после установки.

Один непоставляемый файл core/components/cookieconsent/adapter-checksums.json хранит schema, current (последняя завершённая синхронизация), versions (version → path → SHA256) и короткий итог последней синхронизации. Это только контрольные суммы: без копий JS, БД, редактора и интерфейса истории. Все последующие версии добавляют свои исходные SHA256; совпадающая version с другими исходными checksum отвергается. Исторические hashes позволяют сохранить удаление файла, даже если он исчезал из промежуточного пакета и затем появился снова.

При первом native обновлении 1.0.6 старые hashes берутся из preflight snapshot. При последующих обновлениях уже записанная baseline является авторитетной, в том числе после частичной файловой ошибки. Старая baseline атомарно фиксируется до изменений services/, новая — после синхронизации, до компиляции. Последовательность не является общей транзакцией MODX.

## Правила файлов

| Файл | Действие |
| --- | --- |
| Bytes равны baseline прошлой версии | Обновить оригиналом нового пакета |
| Bytes уже равны новому оригиналу | Оставить, повторная запись не нужна |
| Изменён пользователем | Сохранить точно |
| Изменён и пакетный оригинал | Сохранить пользовательский вариант, зарегистрировать конфликт |
| Ранее поставлялся, сейчас отсутствует | Не восстанавливать |
| Новый путь, свободен, предыдущая baseline достоверна | Добавить |
| Новый путь занят пользовательским файлом | Сохранить существующий файл |
| Нет достоверной baseline | Не заменять существующие и не восстанавливать потенциально удалённые файлы |
| Дополнительный пользовательский файл | Не читать для исполнения и не менять |

Не используется mtime или информация о способе редактирования. Автоматического слияния JS нет. Произвольные JS не сканируются: действует фиксированный manifest inputs. Новые адаптеры требуют явного включения разработчиком в manifest/transport. Hashes исходников оригиналов пакета проверяются строго; пользовательский каталог не сравнивается безусловно с hashes новой версии.

Symlinks, hardlinks и неканонические пути для управляемых файлов отвергаются. Перед rename повторно проверяется ожидаемый hash либо отсутствие файла. FTP/IDE, не соблюдающие lock, не дают общей filesystem-транзакции: не редактируйте тот же файл одновременно с установкой. Отдельного протокола блокировок или механизма слияния не введено.

## Ошибки и восстановление

На обновлении отсутствующий обязательный исходник или некорректный JS сохраняется как пользовательское состояние. При наличии последнего рабочего cached bundle он продолжает обслуживать посетителей с прежним timestamp; Manager показывает ошибку. Исправьте исходник или восстановите удалённый файл вручную, затем очистите кеш из Manager или нажмите существующую кнопку. Пакет не восстанавливает пользовательские файлы ради успешной сборки.

На первой установке нет prebuilt fallback: без рабочего bundle финальный hook возвращает failure. Ошибка прав/зависимостей должна отсеиваться preflight, но поздний сбой после file/object vehicles может оставить частичную установку. Native transport не обещает полного rollback. Сохраняйте backup; после исправления прав/кода повторите установку. Не считайте runtime-файлы или созданные DB elements доказательством успешной Package Management установки.

Ошибка синхронизации (integrity, небезопасный путь, запись baseline/оригинала) прерывает установку даже при старом bundle. Ошибка только сборки после завершённой синхронизации допускает сохранение работоспособного обновления с видимой ошибкой, если прежний cached bundle действительно существует. Диагностика ограничена кодом причины/классом и количеством конфликтов, без пользовательского JS и secrets.

На запросах посетителей нет checksums, stat/read JS, rebuild, fallback discovery или SQL за bundle version. До первого сохранённого timestamp Assets не подключает несуществующий JS. На upgrade старый prebuilt файл может остаться на диске, но новый Assets его не выбирает. Сборка выполняется при install/upgrade, Manager cache clear и ручной force rebuild.

Uninstall нового пакета удаляет только поставленные originals/runtime и plugin, сохраняя services/, generated bundle и checksum metadata как непоставляемые файлы. Как и ранее, не выполняйте uninstall старого пакета поверх новой версии: старые vehicles нельзя изменить задним числом. Удаление active bundle вручную не отслеживается посетителями; восстановите административной сборкой. Read-only hosting больше не может выполнить первую установку без создания bundle.

CLI installer не копирует runtime. Если копирование уже затёрло старый manifest и checksum metadata ещё нет, он консервативно сохраняет существующие файлы; полноценный upgrade с legacy baseline выполняйте native transport. PHP/Peast поставляется в пакете, Node/npm/Composer на клиентском сайте не нужны. Esbuild остаётся в репозитории для CI и differential; CSS сохраняет прежнюю схему.
