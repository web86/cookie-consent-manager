# Универсальные сервисы MODX 2 — 1.0.4-beta1

## Правило согласий

Посетитель управляет **только категориями**: `analytics`, `marketing`, `external_content`. Администратор добавляет, удаляет, включает сервисы и свободно назначает любую из этих трёх категорий. `necessary` остаётся системной. Рекомендация адаптера задаёт лишь начальный выбор.

```js
service.enabled === true && consent.categories[service.category] === true
```

Это условие едино для Метрики, GA4, Ads, GTM, пикселей, карт и custom_js. Разрешение категории запускает **все включённые сервисы** в ней. Индивидуальных переключателей и `consent.providers` в новом выборе нет. Перед запуском CMP проверяет актуальность сохранённой категории: policy, TTL, видимость и её версию. Отозванная/скрытая/устаревшая категория не считается разрешённой.

Consent Mode рассчитывается отдельно от запуска. Например, Ads в analytics загружается при разрешении analytics без дополнительного marketing. Без разрешённого маркетинга `ad_storage`, `ad_user_data`, `ad_personalization` остаются denied и персонализация в config выключена. Для тегов GTM программист обязан настроить consent checks: загрузка контейнера не даёт всем тегам права на обработку. Consent Mode сам по себе не блокирует произвольный Custom HTML.

## Добавление и категории — администратору

Откройте «Компоненты → Cookie Consent Manager → Сервисы», нажмите **+ Добавить сервис** сверху. Выберите готовый адаптер либо **+ Создать пользовательский сервис**. Если адаптер уже настроен, можно перейти к его карточке или создать дополнительный экземпляр с другим ID. Не создаются фиктивные интеграции: Bitrix24 подключается как custom_js.

Новая карточка выключена: заполните поля, выберите категорию, включите сервис, нажмите общий **Сохранить**. До Save меняется только черновик. Категория есть в индивидуальных настройках каждого сервиса. При переносе карточка переходит в новую группу без потери несохранённых полей. За классификацию по реальному назначению отвечает администратор. Дополнительную карточку можно удалить; штатную — выключить.

Видимость каждой категории включается отдельно и сохраняется явно. Добавление/перенос её не включает. Скрытие и повторное включение не восстанавливают старое разрешение. Изменение состава обработки обновляет версию затронутых категорий; посетитель делает новый выбор для этих групп. Другие категории продолжают действовать.

## Свой JavaScript — совместная работа администратора и программиста

Программист размещает файл на тестовом сайте, например `/assets/js/integrations/bitrix24.js`. При ином `assets_url` используется фактический путь от корня origin, включая подкаталог установки MODX, например `/static/company/js/integrations/bitrix24.js`.

Администратор создаёт пользовательский сервис: название, описание/назначение, категория, путь к JS, enabled. `key` и `purpose_id` генерируются и сохраняются компонентом. JSON вручную редактировать не требуется. Для программиста пример отдельного реестра:

```json
{"schema":1,"services":[{"key":"bitrix24","purpose_id":"crm.chat","loader":"custom_js","name":"Bitrix24","purpose":"Онлайн-чат и передача обращений в CRM","category":"marketing","enabled":true,"config":{"path":"/assets/js/integrations/bitrix24.js"}}]}
```

Путь принимает только канонические ASCII сегменты и окончание `.js`. Внешние URL/CDN, схемы, protocol-relative URL, `%`-кодировки, `.`/`..`, обратные слеши, пробелы, query и fragment запрещены. Один путь нельзя назначать разным сервисам, включая выключенные. Владелец должен исключить собственные alias/redirect к одному SDK и прямые script-теги, обходящие CMP. Внешний SDK при необходимости подключает проверенный локальный wrapper. Inline JS, HTML, `eval` и `new Function` из Manager не выполняются; файл не загружается и не исполняется сервером.

До согласия нет активного script src и запроса к файлу. Разрешённая категория запускает каждый включённый JS-файл один раз на страницу; ошибки изолированы от других загрузчиков. После reload актуальное согласие действует. Preview в Manager работает в sandbox/CSP без scripts/network и пользовательский JS не выполняет.

[Минимальный файл](../examples/integrations/local-service.js) показывает простой запуск. [Bitrix24 wrapper](../examples/integrations/bitrix24.js) находит свой экземпляр по пути текущего файла и использует `onAllowed(category, callback, {service})` с `stillAllowed()` до и после async-операций. `service` в API проверяет только наличие включённого сервиса в назначенной категории; отдельного согласия на него нет. Пример использует намеренно нерабочий `example.invalid`: программист задаёт точный проверенный SDK host своего аккаунта и готовит локальный JSON endpoint. Production IDs, действующих клиентских адресов и секретов в репозитории нет. Примеры автоматически не устанавливаются в сайт.

## Версии категорий и миграция

Реестр остаётся schema 1. При обычном Save сервер сравнивает эффективный состав каждой категории: включённые key/loader, исходное назначение purpose, purpose_id и privacy config с boolean defaults. Добавление включённого сервиса, включение/отключение, удаление, изменение privacy config или назначения увеличивает версию своей категории; перенос включённого сервиса — исходной и целевой. Добавление выключенного сервиса ничего не запускает и версию обработки не меняет до его включения. Изменения имени, переводов, текста карты, show_title и порядка карточек сами по себе версию не меняют. Переданные клиентом версии не могут отменить серверное увеличение. Используйте штатный Save/API; прямое редактирование БД обходит этот механизм.

Новый браузерный выбор — `model: categories_v2`, объект `categories`, `category_versions`, policy version, savedAt и consentId. В нём нет providers/disclosed/fingerprints. Fingerprint v2 старых встроенных сервисов сохранён **только для одноразовой миграции** прежнего выбора. При обновлении без изменений категории сохраняются, если старое согласие действительно покрывало все текущие включённые сервисы группы. Если старое согласие было частичным или состав изменился, вся затронутая категория требует нового выбора; остальные сохраняются. Это намеренно консервативная миграция без расширения старого индивидуального разрешения на всю группу.

Точный прежний JSON сохраняется в локальном `web86_cookie_consent_legacy_v2` для обратимой проверки; он никогда не используется загрузчиками. consentId и прежний срок согласия сохраняются. Upgrade не переписывает неизменённые DB registry/texts/options, не создаёт дубликаты и не вызывает глобальный reconsent. Существующая нормализация ранее удалённого clientId остаётся прежней.

Новые события аудита используют **schema 3**: те же события категорий и общие UTC/ID/policy поля, но без providers/provider. Старые schema 1/2, включая исторические map/provider actions, остаются читаемыми, экспортируемыми и неизменёнными. При смешанной выдаче старого HTML после upgrade schema 2 всё ещё принимается для совместимости; новые страницы её не создают. Никакие JSONL не переписываются.

## Карты и тексты

`CookieConsentMap` принимает key экземпляра в `provider`, включая дополнительные карты. Сохраняются прежние `data-cc-map-provider` + inert `data-cc-map-src`, HTTPS host/path/query validation. Карта следует своей категории в любой из трёх групп; до действительного разрешения iframe не создаётся. Кнопка «Настроить категорию для карты» **только открывает настройки**, не отмечает категорию и не обходит отказ. После явного выбора и Save запускаются все включённые сервисы категории, включая её карты. Для скрытой категории кнопки нет. Скрытых индивидуальных map grants больше нет.

Во вкладке **Тексты** выберите язык и редактируйте общее поле `map_notice` либо `service.<key>.map_notice` конкретной карты. `{provider}` подставляет локализованное имя. Fallback: индивидуальный текст текущего языка → общий текст текущего языка → стандартный языковой fallback (для отсутствующего языка — базовый/EN). Прежние переводы не удаляются. Поля — обычный текст, HTML/JS не исполняются. Preview показывает карты по loader независимо от их категории. Текстовые изменения не меняют цель обработки, policy или версии категорий.

## Отзыв и границы ответственности

Отзыв сразу блокирует новые штатные загрузки и callbacks/guards, удаляет iframe, затем перезагружает страницу через прежний механизм с ограниченным ожиданием аудита. После reload отозванные сервисы не запрашиваются. Уже выполненный JS и отправленные запросы автоматически отменить нельзя. Во время ожидания reload произвольный код может продолжить работу; async SDK нужен consent-aware wrapper, а при необходимости свой cleanup.

CMP управляет согласием, **не является sandbox**: после запуска файл получает обычные права JS сайта. CSP отдельно ограничивает источники, но не хранит выбор посетителя. Не считайте CMP изоляцией произвольного кода.

## Где находится код

В каждой карточке Manager есть справка об исходнике. Для программиста: адаптеры и custom loader — `assets/js/cookie-consent/provider-registry.js`, функция start(); категории/persistence/callbacks/карты — `assets/js/cookie-consent/consent-manager.js`; PHP allowlist — `server/src/CookieConsentServiceRegistry.php`; versioning — `CookieConsentSettings::categoryProcessing()` и Save; SSR — `CookieConsentBannerRenderer.php`. В transport поставляется bundle `cookie-consent.min.js`, пересборка — `npm run build:frontend`. Код сайта храните отдельно от компонента.

## Проверка в Manager и Network

1. На staging откройте новый профиль браузера, DevTools → Network, Preserve log и Disable cache. До выбора нет запросов custom JS, SDK и iframe. Отказ и reload сохраняют блокировку.
2. Разрешите одну категорию и сохраните: загружаются все её включённые сервисы, другие группы и выключенные сервисы не запускаются. Повторное применение consent не дублирует скрипты. Reload сохраняет действующий выбор.
3. Отзовите категорию: после автоматического reload запросов нет. Измените состав/назначение/путь через Manager: версия затронутой категории увеличивается и она требует нового выбора. Проверьте сохранность других категорий.
4. Проверьте Ads/GTM в analytics и external_content: адаптер загружается, рекламные сигналы при denied marketing не предоставляются. Проверьте consent checks самих тегов.
5. Проверьте карту в каждой группе, отказ, кнопку настроек, скрытую группу и недопустимый embed URL. Проверьте RU/EN, keyboard, preview и повторное открытие Manager после Save.
6. В журнале для `2026-10-15T11:25:30Z` таблица показывает `15.10.2026 14:25:30`, МСК (UTC+03:00). Детали «Дата и время сервера (UTC)» сохраняют ISO/Z; JSONL и CSV остаются UTC. Поиск, сортировка, история и пагинация прежние.
