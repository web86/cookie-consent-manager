# Ручное тестирование обновления Cookie Consent Manager

Только тестовые сборки: **MODX 2 — cookieconsent 1.0.7-beta2** и
**MODX 3 — cookieconsent3 0.1.0-beta6**. Семейства независимы; MODX 2 ZIP нельзя
устанавливать в MODX 3, и наоборот. Пакеты не опубликованы как стабильные.

## Перед обновлением

1. Сохраните обычный backup БД и файлов сайта. Дополнительно сохраните текущие
   `assets/components/cookieconsentmanager3/js/cookie-consent/services/`, все собственные JS-файлы по настроенным
   путям, `cached-cookie-consent.min.js` и текущее значение `cookie_consent.bundle_version`.
2. Сохраните приватный `core/components/cookieconsent/` с прежним
   `frontend-manifest.json` и `adapter-checksums.json`, если последний существует.
   Сохраните каталог JSONL-журналов и приватную audit-конфигурацию обычным закрытым
   способом. Для перехода со старого релиза старый manifest нужен для точного
   начального SHA256 baseline: не удаляйте его до установки нового пакета.
3. Зафиксируйте Strict/Legacy, TTL, кнопки, видимость категорий, сервисы/ID/параметры,
   custom JS-пути, тексты RU/EN и каталог журнала. Посчитайте SHA256 изменённых
   адаптеров и собственного JS; отдельно запишите намеренно удалённые файлы.
4. Проверьте PHP 8.1+ и совместимую платформу (проверено на MODX 2.8.8 / 3.2.4).
   Установщик должен иметь обычные права записи в каталог bundle и приватный
   каталог компонента. Node/npm/Composer на сервере клиента не требуются.

## Установка через Package Manager

1. Сверьте имя, размер и SHA256 архива с отчётом данной сборки. Не подменяйте
   архив уже установленной signature другими bytes. Используйте только выданный
   итоговый ZIP; прежние synthetic test fixtures не предназначены для установки.
2. Откройте штатное управление пакетами MODX и загрузите локальный transport ZIP.
   Если используете локальный поиск пакетов, поместите ZIP в каталог
   `{core_path}packages/` установленного MODX и выполните штатный поиск.
3. Установите новую версию поверх компонента: **1.0.6 → 1.0.7-beta2** либо
   **0.1.0-beta4 → 0.1.0-beta6**. **Uninstall старой версии не выполнять.**
4. Дождитесь результата Package Manager. При ошибке не считайте установку
   завершённой: native transport может оставить частичное состояние. Сохраните
   диагностику и используйте обычный backup-процесс; отдельного механизма rollback
   эти тестовые сборки не добавляют.
5. После успешной установки один раз очистите кеш штатной командой Manager и
   перезагрузите страницу компонента/браузерный кеш. При установке PHP уже создаёт
   bundle либо сохраняет прежний рабочий файл при ошибке; очистка кеша проверяет
   административный hook и обновляет страницы. Посетительские запросы не собирают JS.

## Проверка адаптеров и статуса

1. Сравните сохранённые SHA256 пользовательских изменений и custom JS: bytes
   должны сохраниться. Дополнительные файлы остаются на месте. Намеренно
   удалённые встроенные адаптеры не должны появиться автоматически.
2. В приватном `adapter-checksums.json` проверьте наличие старого и нового baseline,
   новую `current` и отчёт о сохранённых изменениях/удалениях. Это hashes исходников
   пакета, а не обещание автоматического слияния пользовательского JavaScript.
3. Откройте «Настройки → Дополнительные настройки → Сборка адаптеров».
   Проверьте реальный статус и дату. Нажмите «Пересобрать адаптеры»; успех допустим
   только после ответа операции, дата должна обновиться. Кнопка не сохраняет draft.
4. Пользовательские JS-файлы загружаются отдельно и не входят в общий bundle.
   Если намеренно удалён обязательный input или в нём ошибка JS, пересборка
   ожидаемо показывает ошибку и сохраняет предыдущие bundle/SHA256/дату успеха.
   Восстановление или исправление такого файла — осознанное решение владельца;
   установщик не восстанавливает его автоматически ради компиляции.
5. Не повреждайте рабочий адаптер ради проверки на основном сайте. Негативный
   сценарий выполняйте только на отдельной копии с сохранённым исходником и bundle.

## Проверка UI, журнала и frontend

- Убедитесь, что версия в Manager соответствует новому пакету. Сверьте все
  прежние настройки. Дополнительная карточка закрыта по умолчанию; измените поле
  журнала, закройте карточку и сохраните — значение должно сохраниться.
- Проверьте предупреждение Legacy, руководство и кнопки действий. Повторный запрос
  согласия показывается с подтверждением и действительно затрагивает всех
  посетителей: проверяйте его только на копии/в момент запланированного reconsent.
- В форме нового сервиса первым выбран «+ Создать пользовательский сервис».
  Откройте существующий сервис, сохраните без смены adapter и проверьте его ID,
  параметры и путь. В карточке показывается путь исходника без технического хвоста.
- Переключите RU/EN Manager и убедитесь, что новые подписи локализованы.
- Исторические JSONL должны остаться неизменными. В журнале проверьте «Страница»,
  поиск, фильтры, следующую страницу, детали и CSV. Для старой записи без пути
  отображается «—»; CSV использует прежнюю единственную колонку Page/Страница.
- Совершите одно тестовое действие согласия на странице с query/hash. В новом
  событии должен сохраниться только pathname. Не должно быть дополнительных
  событий от обычного просмотра страниц или очистки кеша.
- В чистом профиле браузера проверьте Strict: до согласия нет сторонних запросов,
  карт/видео/iframe и соответствующих callbacks; после согласия они работают один
  раз. Перезагрузите страницу, затем отзовите согласие и проверьте блокировку.
- Для Legacy проверьте прежнюю семантику первого посещения, сохранённого согласия
  и отказа. Не меняйте режим основного сайта только ради теста. Проверьте собственные
  `onAllowed` callbacks, внешние SDK и реальные плееры с вашими ID/CSP/ограничениями.

## Ошибки и диагностика

Признаки ошибки: Package Manager сообщает failure; UI не открывается; PHP/JS
exception; незапрошенная смена настроек/adapter; потеря пользовательских bytes,
журнала или старого bundle; ложный успешный статус; query/hash в новой записи;
сторонние запросы в Strict до согласия.

Соберите signature и SHA256 ZIP, версию MODX/PHP/компонента, время и шаги,
статус/дату сборки, код HTTP и request_id при наличии, PHP error.log за этот
интервал, JS console/network errors, список проблемных путей и их hashes/права.
Не передавайте секреты audit, пароли, modAuth/токены; JSONL содержит данные
посетителей и не должен публиковаться целиком.

MODX 3: сторонний pdoTools3 3.1.0 warm Fenom cache NO-GO не исправляется этими
пакетами и не является результатом release preparation Cookie Consent Manager.
Выполняйте Fenom-проверку отдельно от обычной интеграции компонента.
