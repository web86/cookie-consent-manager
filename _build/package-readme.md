Cookie Consent Manager — native MODX 2 package (beta11)

No Setup Options or package-state directory. Open Extras → Cookie Consent Manager. On Log choose website-relative storage (e.g. /logs/cookies/) or an absolute private directory, then Check and enable journal. Other form edits use Save. A private directory outside DOCUMENT_ROOT is recommended. A public Apache directory requires real HTTP 403 protection proof; existing administrator .htaccess is preserved; nginx, proxies/CDN and unknown servers require private storage. Legacy environment/private JSON configuration remains supported and takes precedence.

Public preferences expose four categories only. Active providers stay internal; newly added/changed services and legacy partial permissions require review and never expand silently.

Managed setup stores origin/rate in cookie_consent.audit and a random HMAC key in the native server-side MODX DB Registry (never system config JS or public registry). Protect DB/backups/core. No secret is generated by installation itself. POST testing adds a real test event; old logs are never removed.

Add [[!CookieConsent]] once to a shared template. Remove old direct analytics scripts and noscript pixels. Use CookieConsentMap separately on map pages with reviewed HTTPS embed URLs. No templates are edited by installation; optional services start disabled. The unified snippet uses live mode by default; mode=mock is only for isolated acceptance tests.

Settings, all existing translations/notice HTML/service parameters, browser consent and JSONL are preserved. Active chunks/snippets are NEVER overwritten. Compare *_package_VERSION stock copies and apply changes explicitly. Ordinary text edits preserve consent; only the confirmed advanced reconsent action changes policy version.

Back up DB (including native registry tables), elements/templates, customized runtime, private legacy config and JSONL before upgrading. Native file vehicles replace package runtime files; direct changes require backup/merge. MODX core/packages native archives help recovery, but partial DB/filesystem errors are not atomic and no custom rollback is promised.

Uninstall removes exact shipped files and retains settings/elements/menu/ACL, native audit key/config, logs and untracked files. Remove template connections first; retained menu/elements can refer to removed code. Full purge is an explicit administrator decision. Do not run superseded ledger-based beta uninstall over a newer installation.
